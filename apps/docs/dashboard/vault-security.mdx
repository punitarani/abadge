---
title: "Vault security"
description: "Change the master password, set up a recovery key, and rotate the profile root key."
---

The **Vault security** page lives on each profile detail view. It exposes operations that touch the encryption material directly. All of them happen client-side for zero-knowledge profiles — the server only sees the new wrapped material.

## Change master password

Re-wraps the existing root key under a new KEK derived from a new password. The root key itself is unchanged — every existing item remains decryptable.

<Steps>
  <Step title="Open Vault security → Change master password">
    Available on profile detail pages for zero-knowledge profiles.
  </Step>
  <Step title="Enter the current password">
    The browser derives the old KEK and unwraps the root key. If the old password is wrong, the unwrap fails — abadge does not check passwords directly.
  </Step>
  <Step title="Enter and confirm the new password">
    The browser generates a new 16-byte salt and derives a new KEK via Argon2id (64 MiB memory, 3 iterations).
  </Step>
  <Step title="Wrap and ship">
    The new wrapped root key, salt, and KDF parameters are sent to the password-change operation. The profile envelope is replaced atomically.
  </Step>
</Steps>

<Note>
  Existing recovery keys still work — the root key didn't change. You only need to redo recovery setup if you generated a new root key.
</Note>

## Set up recovery

Without recovery, losing your master password means losing every item in a zero-knowledge profile. Recovery adds a second wrap of the root key under a 256-bit recovery key.

<Steps>
  <Step title="Open Vault security → Set up recovery">
    Click **Generate recovery key**.
  </Step>
  <Step title="Save the recovery key">
    The dashboard displays a 52-character base32 recovery key, grouped in fives:
    ```
    ABCDE-FGHIJ-KLMNO-PQRST-UVWXY-Z2345-67ABC-DEFGH-IJKLM-NOPQR-STUVW
    ```
    **Store it offline.** Print it, write it down, or save it in a separate password manager. abadge does not retain the value.
  </Step>
  <Step title="Confirm">
    The browser wraps the root key with the recovery key (XChaCha20-Poly1305) and ships the `recoveryWrappedRootKey` to the recovery-setup operation.
  </Step>
</Steps>

<Warning>
  The recovery key is the only way to restore access if you forget the master password. There is no server-side recovery for zero-knowledge profiles.
</Warning>

## Rotate root key

Generates a fresh root key and re-wraps every item DEK. Use this if you suspect the root key has been exposed — for example, after a stolen browser tab or an old laptop.

<Steps>
  <Step title="Unlock the profile">
    The browser must hold the current root key in memory.
  </Step>
  <Step title="Generate a new root key">
    32 random bytes.
  </Step>
  <Step title="Re-wrap every DEK">
    The browser walks every item, decrypts the DEK with the old root key, and re-wraps with the new one.
  </Step>
  <Step title="Wrap the new root key">
    Once with the current KEK. Once with the recovery key (if recovery is set up).
  </Step>
  <Step title="Ship the batch">
    Send the new wrapped keys plus the rekeyed items map to `POST /v1/profiles/{profileId}/rotate`. The server applies all updates in a single transaction and increments `keyVersion`.
  </Step>
</Steps>

<Note>
  The plaintext payload of every item is unchanged — only the wrap changes. There's no risk of mangling values during rotation.
</Note>

If your client misses any items, the server returns `ROTATE_KEY_INCOMPLETE` with the missing IDs in `meta.missingItemIds`. Re-fetch and retry.

## Server-managed profiles

Server-managed profiles do not expose vault security operations — there is no master password and no client-side root key. Server key rotation (changing the Worker's `ENCRYPTION_KEY`) is an operational task handled outside the dashboard.

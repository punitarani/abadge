title: "Permissions"
description: "Grant capabilities to agents on individual items, with optional expiries."
---

The **Permissions** view is where you connect agents to the secrets they can use. A grant can target a **single item** or an **entire profile** (every item in the profile, now and in the future). Each grant is one row at the storage level (agent + target + capability), but the dashboard groups grants by `(agent, target)` so a single line shows every capability the agent has on that target.

## Listing permissions

The permissions table groups rows by `(agent, target)` pair, where the target is an item or a profile. Each row shows:

- Agent name and kind
- Target — item label and storage mode, or the profile name for profile-wide grants
- Capabilities — one chip per granted capability, with `read` before `use`
- Expires — the soonest deadline among the group's capabilities, or "Mixed" when capabilities have different expiries
- A small `✕` on each chip to revoke that one capability without touching the others

Filter and search remain row-level (agent / capability / expiry, plus a text search over agent and target), then groups are formed from the filtered rows.

## Creating a permission

Click **Grant permission** to open the panel.

<Steps>
  <Step title="Select an agent">
    Only enabled, non-revoked agents are listed.
  </Step>
  <Step title="Choose a target">
    **Single item** grants access to one credential. **Entire profile** grants access to every item in the profile, now and in the future. Then pick the item or profile.
  </Step>
  <Step title="Pick one or more capabilities">
    The dashboard shows only capabilities valid for the chosen agent + target, based on the [capability matrix](/concepts/permissions-and-capabilities) (for a profile target, it intersects the matrix across the profile's current items). Tick as many as you need — multi-grant is atomic. A capability the agent already holds on the target is dimmed and labelled "already granted".
  </Step>
  <Step title="(Optional) Set an expiry">
    A date. Applies to every capability you ticked in this submission. Leave blank for non-expiring grants. To grant some capabilities with one expiry and others with another, submit two batches.
  </Step>
  <Step title="Save">
    The whole batch lands atomically — every ticked capability becomes one row, all in one transaction. Future access attempts check those rows.
  </Step>
</Steps>

<Warning>
  Granting **`read` on an entire profile** hands the agent the plaintext of every credential in the profile, now and forever. The dashboard surfaces a confirmation dialog before this specific grant and suggests `use` instead — the agent runs processes with the secret but never sees it.
</Warning>

The composite unique constraint `(agentId, itemId, capability)` means each triple has at most one row. The router pre-checks for duplicates so the error envelope can list every conflicting capability up front (`meta.duplicateCapabilities`).

## Capability cheatsheet

| Capability | Use when |
|---|---|
| `read` | Read a secret's value — a local agent gets the encrypted blob to decrypt via the daemon (zero-knowledge items), or plaintext over HTTPS (server-managed). The only capability available to remote agents. |
| `use` | The CLI or MCP should inject the secret for local consumption — `delivery: env` injects into a subprocess env var, `delivery: file` writes a temp file with `0600` permissions. |

Invalid combinations (for example, a remote agent + `use`) are rejected at create time with `INVALID_CAPABILITY_LOCALITY` or `INVALID_CAPABILITY_STORAGE`.

## Revoking a permission

Each capability chip has its own `✕` button. Clicking it deletes that single permission row immediately — sibling capabilities on the same `(agent, item)` pair are untouched. Any in-flight access attempt that hasn't yet checked the row sees the deletion and is denied. Audit entries get `permission.revoke` (one per capability revoked) and `permission.revoke_cascade` for cascaded denials.

## Expiring permissions

Set `expiresAt` to a future ISO timestamp when granting. The server treats a permission as missing once the time passes. Audit entries show `result: expired`.

There is no auto-renewal. To extend a permission, revoke and re-grant with a later expiry.

## Common patterns

| Goal | Setup |
|---|---|
| CI runner needs DB password | Remote agent + server-managed item + `read` + 24-hour expiry |
| Local script needs an API key on demand | `local_cli` agent + any item + `use` (delivery: env) |
| MCP server runs a CLI tool with a token | `local_mcp` agent + any item + `use` (delivery: env) |
| Local script needs to mount a TLS key as a file | `local_cli` agent + any item + `use` (delivery: file) |
| Local app needs the encrypted blob to decrypt offline | `local_cli` agent + zero-knowledge item + `read` |

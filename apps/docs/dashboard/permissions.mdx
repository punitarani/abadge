The **Permissions** view is where you connect agents to the items they can use. Each grant is still one row at the storage level (agent + item + capability), but the dashboard groups grants by `(agent, item)` so a single line shows every capability the agent has on that item.

## Listing permissions

The permissions table groups rows by `(agent, item)` pair. Each row shows:

- Agent name and kind
- Item label and storage mode
- Capabilities — one chip per granted capability, with the canonical order (`read_ciphertext` → `reveal_plaintext` → `mount_env` → `mount_file`)
- Expires — the soonest deadline among the group's capabilities, or "Mixed" when capabilities have different expiries
- A small `✕` on each chip to revoke that one capability without touching the others

Filter and search remain row-level (agent / item / capability / expiry), then groups are formed from the filtered rows. The footer shows both the row count and the pair count.

## Creating a permission

<Steps>
  <Step title="Click Grant permission">
    Select an agent and an item from the dropdowns.
  </Step>
  <Step title="Pick one or more capabilities">
    The dashboard shows only capabilities that are valid for the chosen agent + item combination, based on the [capability matrix](/concepts/permissions-and-capabilities). Tick as many as you need — multi-grant is atomic.
  </Step>
  <Step title="Already-granted capabilities">
    If the agent already has a capability on the chosen item, that capability is dimmed and labelled "already granted" — you can't accidentally re-pick it. (The backend would reject a duplicate with `PERMISSION_ALREADY_EXISTS` anyway.)
  </Step>
  <Step title="(Optional) Set an expiry">
    ISO date. Applies to every capability you ticked in this submission. Leave blank for non-expiring grants. To grant some capabilities with one expiry and others with another, submit two batches.
  </Step>
  <Step title="Save">
    The whole batch lands atomically — every ticked capability becomes one row, all in one transaction. Future access attempts check those rows.
  </Step>
</Steps>

The composite unique constraint `(agentId, itemId, capability)` means each triple has at most one row. The router pre-checks for duplicates with one `IN` query so the error envelope can list every conflicting capability up front (`meta.duplicateCapabilities`).

## Capability cheatsheet

| Capability | Use when |
|---|---|
| `read_ciphertext` | A local agent needs the encrypted blob to decrypt via the daemon (zero-knowledge items only). |
| `reveal_plaintext` | Plaintext should be returned over HTTPS (server-managed only). The default for remote agents. |
| `mount_env` | The CLI or MCP should inject the secret into a subprocess env var. |
| `mount_file` | The CLI or MCP should write the secret to a temp file with `0600` permissions. |

Invalid combinations (for example, a remote agent + `mount_env`) are rejected at create time with `INVALID_CAPABILITY_LOCALITY` or `INVALID_CAPABILITY_STORAGE`.

## Revoking a permission

Each capability chip has its own `✕` button. Clicking it deletes that single permission row immediately — sibling capabilities on the same `(agent, item)` pair are untouched. Any in-flight access attempt that hasn't yet checked the row sees the deletion and is denied. Audit entries get `permission.revoke` (one per capability revoked) and `permission.revoke_cascade` for cascaded denials.

## Expiring permissions

Set `expiresAt` to a future ISO timestamp when granting. The server treats a permission as missing once the time passes. Audit entries show `result: expired`.

There is no auto-renewal. To extend a permission, revoke and re-grant with a later expiry.

## Common patterns

| Goal | Setup |
|---|---|
| CI runner needs DB password | Remote agent + server-managed item + `reveal_plaintext` + 24-hour expiry |
| Local script needs an API key on demand | `local_cli` agent + any item + `mount_env` |
| MCP server runs a CLI tool with a token | `local_mcp` agent + any item + `mount_env` |
| Local script needs to mount a TLS key as a file | `local_cli` agent + any item + `mount_file` |
| Local app needs the encrypted blob to decrypt offline | `local_cli` agent + zero-knowledge item + `read_ciphertext` |

The abadge API is a JSON REST API served under the `/v1` prefix. Every
operation — organizations, profiles, items, agents, permissions, secret
access, and audit — is a `/v1` endpoint authenticated with a bearer token.

## Base URLs

| Environment | Base URL |
|---|---|
| Production | `https://api.abadge.io/v1` |
| Local development | `http://localhost:8787/v1` |

The OpenAPI 3.1 spec is served at `/v1/openapi.json`. The reference pages in
this section are generated from that spec, so the documentation and the live
API cannot drift apart.

## Conventions

<ParamField path="Content type" type="application/json">
  Request and response bodies are JSON.
</ParamField>
<ParamField path="Path parameters" type="string">
  Appear in curly braces, e.g. `/items/{itemId}`.
</ParamField>
<ParamField path="Request IDs" type="header">
  Every response includes an `X-Request-Id` header. Set your own and the
  server echoes it back — include it when reporting issues.
</ParamField>
<ParamField path="Errors" type="envelope">
  Every non-2xx response is a `{ code, message, hint, meta }` envelope.
  Validation errors add an `issues[]` array. See [Errors](/api/errors).
</ParamField>

## Organization scoping

Most endpoints are scoped to an organization. The server resolves the
caller's org in this order:

<Steps>
  <Step title="Header">
    The `X-Abadge-Org-Id` header, if present.
  </Step>
  <Step title="Sole membership">
    The single org the caller belongs to, when unambiguous.
  </Step>
  <Step title="Bound credential">
    The org embedded in an agent session or personal API key.
  </Step>
</Steps>

<Warning>
  If a user belongs to multiple orgs and omits `X-Abadge-Org-Id`, the request
  fails with `400` and `code: "ORG_HEADER_REQUIRED"`. The error's
  `meta.availableOrgIds` lists the user's orgs.
</Warning>

## A first request

<CodeGroup>
```bash cURL
curl https://api.abadge.io/v1/items \
  -H "Authorization: Bearer abu_..." \
  -H "X-Abadge-Org-Id: org_..."
```

```ts SDK
import { AbadgeUserClient } from "@abadge/sdk";

const client = new AbadgeUserClient({
  apiUrl: "https://api.abadge.io",
  sessionToken: process.env.ABADGE_TOKEN!,
  orgId: "org_...",
});

const { items } = await client.items.list();
```
</CodeGroup>

## Surfaces

| Surface | Path | Purpose |
|---|---|---|
| REST API | `/v1/*` | The public application API documented here |
| Better Auth | `/api/auth/*` | Human authentication and device authorization |
| Agentic registration | `/agent/auth*`, `/.well-known/*`, `/auth.md` | [auth.md](/api/agentic-registration) agent self-registration and human claim |

Human authentication lives at `/api/auth/*` and is not part of `/v1`. See
[Human authentication](/api/auth-routes). Agents can self-register an unclaimed
account through the [agentic registration](/api/agentic-registration) flow.

## Clients

You can call `/v1` with any HTTP client. For TypeScript projects, the
official [SDK](/api/sdk/installation) wraps the API with typed methods,
automatic auth headers, and — for agents — keypair session management.

The `access` router is the audited boundary. Every secret read by an agent runs through one of these procedures, and every attempt — allowed or denied — appends an audit row.

All three procedures are `agentProcedure` — they require an agent bearer credential.

## `access.ciphertext`

Return the encrypted blob of a zero-knowledge item for local-daemon decryption.

**Required capability:** `read_ciphertext`.
**Required item mode:** `zero_knowledge`.
**Required locality:** `local`.

<ParamField path="itemId" type="string" required />

**Returns:**

```ts
{
  encryptedItemKey: string;   // nonce || DEK encrypted by root key (nonce prepended)
  ciphertext: string;          // nonce || payload encrypted by DEK (nonce prepended)
  cryptoVersion: number;
}
```

The 24-byte XChaCha20-Poly1305 nonce is prepended to each blob — the decrypt side splits on the fixed nonce length. No separate nonce fields are returned.

Denied if: remote agent, server-managed item, or missing `read_ciphertext` permission.

Audit: `access.ciphertext` with `result: allowed` or `denied`.

## `access.reveal`

Decrypt and return a field value from a server-managed item.

**Required capability:** `reveal_plaintext`.
**Required item mode:** `server_managed`.
**Required locality:** any.

<ParamField path="itemId" type="string" required />
<ParamField path="field" type="string">
  Named field for multi-field items. See [Field delivery](/concepts/fields).
</ParamField>

**Returns:** `{ payload }` containing the resolved field value.

Errors:

- `MULTI_FIELD_ITEM` when the item has multiple fields and `field` is omitted. `meta.availableFields` lists the names.
- `FIELD_NOT_FOUND` when `field` does not exist.
- `INVALID_CAPABILITY_STORAGE` for zero-knowledge items.

Audit: `access.reveal`.

## `access.mount`

Return data appropriate for local injection (env var or temp file).

**Required capability:** `mount_env` or `mount_file`.
**Required item mode:** any.
**Required locality:** `local`.

<ParamField path="itemId" type="string" required />
<ParamField path="mountType" type="string" required>
  `env` or `file`.
</ParamField>
<ParamField path="field" type="string">
  Named field for multi-field items.
</ParamField>

**Returns:**

For server-managed items:

```ts
{
  storageMode: "server_managed";
  payload: ItemPayload;
}
```

For zero-knowledge items (the daemon decrypts locally):

```ts
{
  storageMode: "zero_knowledge";
  encryptedItemKey: string;   // nonce prepended
  ciphertext: string;          // nonce prepended
  cryptoVersion: number;
}
```

Denied if: remote agent, or missing the corresponding `mount_*` permission.

Audit: `access.mount_env` or `access.mount_file`.

## `access.bulkMountEnv`

Returns every item in the given **profile** that the calling agent has `mount_env` on, in one round trip. Backs `abadge run --all`. Profile is the trust boundary — items in other profiles are NEVER returned, even if the agent has grants on them.

Auth: `agentProcedure` (local agents only).

Input:

```ts
{ profileId: string }
```

Response:

```ts
{
  items: Array<
    | {
        storageMode: "zero_knowledge";
        itemId: string;
        label: string;
        encryptedItemKey: string;
        ciphertext: string;
        cryptoVersion: number;
        profileId: string;
        contentVersion: number;
      }
    | {
        storageMode: "server_managed";
        itemId: string;
        label: string;
        payload: ItemPayload;
      }
  >
}
```

Each included item produces one `access.mount_env` audit row tagged `meta.viaBulk = true` with `profileId` populated.

Failure modes:

- Remote agents → `PERMISSION_DENIED` at the gate (no per-item audit row, since no items were accessed).
- `profileId` belonging to another org → `PROFILE_NOT_FOUND` (existence is not leaked).
- More than 256 matching items → `BAD_REQUEST` with `meta.limit = 256`. Scope further or use single-item `access.mount`.

The CLI normalizes each item's `label` into a POSIX env-var name (`openai-api-key` → `OPENAI_API_KEY`), applies the structural filter (only items with exactly one string field participate), and hard-rejects on collisions or reserved names like `LD_PRELOAD` / `NODE_OPTIONS`. ZK items are decrypted in-process by the daemon; CLI never sees ZK plaintext.

## Decision flow

Every `access.*` call runs the same decision flow before any decryption:

<Steps>
  <Step title="Authenticate the bearer token">
    Resolve the `abs_...` agent session token (hash lookup, TTL check). `access.*` accepts no other credential — personal API keys (`abu_`) are rejected here.
  </Step>
  <Step title="Resolve the item">
    Must belong to the same organization as the agent.
  </Step>
  <Step title="Check the permission row">
    `(agentId, itemId, capability)` must exist.
  </Step>
  <Step title="Check expiry">
    `expiresAt` must be null or in the future. Otherwise `result: expired`.
  </Step>
  <Step title="Enforce the capability matrix">
    Locality and storage mode must match.
  </Step>
  <Step title="Audit the attempt">
    Append the row before returning. Allowed and denied alike.
  </Step>
  <Step title="Decrypt only if authorized">
    Server-managed items are decrypted by the API. ZK items are returned as ciphertext for local decryption.
  </Step>
</Steps>

See [Permissions and capabilities](/concepts/permissions-and-capabilities) for the full matrix.

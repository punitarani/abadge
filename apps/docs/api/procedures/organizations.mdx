The `organizations` router covers the top-level isolation boundary plus member management.

## `organizations.create`

**Tier:** `userProcedure` — requires an authenticated user, but the caller does not need an active organization context. Used for first-org creation during onboarding.

<ParamField path="name" type="string" required>
  Organization display name.
</ParamField>
<ParamField path="slug" type="string">
  URL-safe identifier. Auto-generated if omitted.
</ParamField>

**Returns:** `{ organization, defaultProfile }`. `organization` includes `isPersonal: false`.

## `organizations.createPersonal`

**Tier:** `userProcedure` — requires an authenticated user, but no active-org context. The one-click "Personal account" path in onboarding.

**Input:** none.

Auto-generates a workspace name and slug from the user record (falling back to `"Personal workspace"`), then transactionally seeds a personal org (flagged via `organization.metadata`), the owner `member` row, and a default `server_managed` profile (`name`/`externalId` both `"default"`) — reusing the same seed builder as `organizations.create`.

**Returns:** the same `{ organization, defaultProfile }` shape as `organizations.create`, with `organization.isPersonal: true`.

A personal account is structurally a normal single-member org: it holds one profile by default (more allowed), can hold many agents, and may coexist with team orgs the user creates or joins later.

## `organizations.list`

**Tier:** `userProcedure` — requires an authenticated user; no active-org context needed.

**Input:** none.

**Returns:**

```ts
{
  organizations: Array<{
    id: string;
    name: string;
    slug: string;
    logo: string | null;
    createdAt: string;
    role: "owner" | "admin" | "member";
    hasBootstrappedProfile: boolean;
    isPersonal: boolean;
  }>;
}
```

`hasBootstrappedProfile` is `true` when the org has at least one server-managed profile or a zero-knowledge profile with a non-null `wrappedRootKey`. The dashboard onboarding-resume flow uses it to skip a per-org `profiles.list` round trip. `isPersonal` is `true` for personal accounts (orgs flagged via `organization.metadata`); the dashboard labels these "Personal" rather than "Organization".

## `organizations.members.invite`

**Tier:** `sessionProcedure` (admin or owner)

<ParamField path="orgId" type="string" required />
<ParamField path="role" type="string">
  `owner`, `admin`, or `member`. Defaults to `member`.
</ParamField>

**Returns:**

```ts
{
  ok: true;
  invitationId: string;
  token: string;       // abi_... shown once
}
```

Only the SHA-256 hash of `token` is stored. Invitations expire after 7 days. The frontend builds the URL: `{APP_URL}/invite/accept?token={token}`.

<Note>
  The invite procedure does not take an email address. The recipient's identity is bound at accept time — anyone holding the token (and signed in) can redeem it. Distribute invite URLs through an authenticated channel.
</Note>

## `organizations.members.getInviteInfo`

**Tier:** `sessionProcedure`

<ParamField path="token" type="string" required />

**Returns:**

```ts
{
  organizationName: string;
  organizationSlug: string;
  role: "owner" | "admin" | "member";
  expiresAt: string;
}
```

Authentication is required to prevent enumeration of org names. Rate-limited to 10 lookups / minute per (user, IP); excess returns `RATE_LIMITED`.

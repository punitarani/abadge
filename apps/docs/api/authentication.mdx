---
title: "Authentication"
description: "Bearer tokens for operators and agents, and the keypair session exchange."
---

Every `/v1` request carries a bearer token:

```http
Authorization: Bearer <token>
```

There are three token types, each for a different caller.

| Prefix | Holder | Reaches `access.*`? | Issued by |
|---|---|---|---|
| Better Auth session | Human operator | No | `/api/auth/sign-in/*` |
| `abu_…` | Personal API key (user + org) | No | `POST /v1/api-keys` |
| `abs_…` | Agent session | **Yes** | `POST /v1/agents/{agentId}/sessions/exchange` |

<Info>
  Only an `abs_…` agent session can read or mount secret values via the
  `/v1/access/*` endpoints. Operator sessions and personal API keys manage the
  control plane but can never reveal a secret.
</Info>

## Human operators

[Better Auth](https://www.better-auth.com) handles operator identity at
`/api/auth/*`. Sign in to obtain a session token (or browser cookie), then use
it as the bearer for `/v1` management endpoints. See
[Human authentication](/api/auth-routes) for the route list and the CLI device
flow.

### Personal API keys

A personal API key (`abu_…`) lets a user script the management surface without
a browser. Each key is bound to a `(user, org)` pair and is created, listed,
and revoked from the dashboard's org Settings page or via the
`POST /v1/api-keys` endpoint.

<Warning>
  A personal API key is **structurally barred** from `/v1/access/*`: it can
  never reveal or mount secret values, and it cannot create or revoke other API
  keys. Reading secrets still requires a keypair agent plus an explicit
  permission. The secret is shown exactly once at creation — the server stores
  only a SHA-256 hash and an 8-character lookup prefix.
</Warning>

## Agents

Agents authenticate with short-lived Ed25519 keypair sessions. The session
token (`abs_…`) is opaque, hashed at rest, and expires after 15 minutes. It is
the only credential that reaches `/v1/access/*`.

### Session lifecycle

<Steps>
  <Step title="Register">
    An operator registers the agent (`POST /v1/agents`) with a public key, or
    requests a one-time `abe_…` bootstrap token.
  </Step>
  <Step title="Enroll">
    A bootstrapped agent redeems its token and uploads its public key
    (`POST /v1/agents/enroll`).
  </Step>
  <Step title="Challenge">
    The agent requests a signing challenge
    (`POST /v1/agents/{agentId}/sessions/challenge`, `abc_…`, 60-second TTL).
  </Step>
  <Step title="Exchange">
    The agent signs the challenge and exchanges it for an `abs_…` session token
    (`POST /v1/agents/{agentId}/sessions/exchange`, 15-minute TTL).
  </Step>
  <Step title="Refresh">
    The SDK re-runs the exchange at T-2 minutes before expiry; no long-lived
    secret is ever stored on disk.
  </Step>
</Steps>

### Token defaults

| Token | Prefix | TTL |
|---|---|---|
| Bootstrap / enrollment | `abe_` | 10 minutes |
| Signing challenge | `abc_` | 60 seconds |
| Agent session | `abs_` | 15 minutes |

## Authorization header examples

<CodeGroup>
```bash Operator session
curl https://api.abadge.io/v1/items \
  -H "Authorization: Bearer <better-auth-session-token>"
```

```bash Personal API key
curl https://api.abadge.io/v1/items \
  -H "Authorization: Bearer abu_..."
```

```bash Agent session
curl https://api.abadge.io/v1/access/itm_.../read \
  -H "Authorization: Bearer abs_..." \
  -X POST
```
</CodeGroup>

## Auth audit events

Every auth lifecycle event is recorded in the audit log:

`auth.login`, `auth.logout`, `agent.bootstrap_issue`, `agent.enroll`,
`agent.session_issue`, `agent.session_reject`, `agent.session_revoke`.

See [Audit log](/concepts/audit-log) for the full catalog.

title: "Authentication"
description: "Configure the MCP server with Ed25519 keypair sessions. Env vars take precedence over the config file."

The MCP server authenticates with **Ed25519 keypair sessions** — the same mechanism `AbadgeAgentClient` uses. It reads configuration from environment variables first, then falls back to `~/.abadge/config.json`.

The MCP server has no other auth method — there are no agent API keys. Every agent authenticates with a keypair session.

## Required configuration

The MCP server needs three things on startup: the API URL, the agent ID, and the agent's Ed25519 private key (either inline or via a file path).

| Variable | Required | Description |
|---|---|---|
| `ABADGE_API_URL` | yes | Base URL of the API (e.g. `https://api.abadge.io`) |
| `ABADGE_AGENT_ID` | yes | Provisioned MCP agent ID |
| `ABADGE_PRIVATE_KEY_PATH` | one of | Path to an Ed25519 private key (JWK file) |
| `ABADGE_PRIVATE_KEY` | one of | Inline Ed25519 private key (JWK JSON string) |

Exactly one of `ABADGE_PRIVATE_KEY_PATH` or `ABADGE_PRIVATE_KEY` must be set. Missing everything makes the server exit with a clear error message.

## MCP-specific overrides

When the same machine runs both the CLI and the MCP server under the same operator, these env vars override the generic values for MCP only:

| Variable | Description |
|---|---|
| `ABADGE_MCP_AGENT_ID` | Overrides `ABADGE_AGENT_ID` for MCP only |
| `ABADGE_MCP_PRIVATE_KEY` | Overrides `ABADGE_PRIVATE_KEY` (inline JWK) for MCP only |

Use these when the CLI and MCP should authenticate as different agents.

## Config file fallback

If an env var isn't set, the MCP server reads `~/.abadge/config.json` at the **top level**:

```json
{
  "apiUrl": "http://localhost:8787",
  "agentId": "agent_...",
  "privateKeyPath": "/Users/you/.abadge/agents/agent_.ed25519.jwk"
}
```

<Warning>
  The MCP server reads the **top-level** `apiUrl`, `agentId`, and `privateKeyPath` fields — not the `localAgents.mcp` object that the CLI writes. Provide these values via environment variables when launching the MCP server from Claude Desktop; see [Claude Desktop config](/mcp/claude-desktop).
</Warning>

## Keypair session lifecycle

On startup, the MCP server:

<Steps>
  <Step title="Load configuration">
    Resolve env vars → fall back to config file → error out if required fields are missing.
  </Step>
  <Step title="Build an anonymous client">
    No bearer set yet.
  </Step>
  <Step title="Request a challenge">
    `auth.createChallenge` returns `abc_...` (60-second TTL).
  </Step>
  <Step title="Sign the challenge">
    Ed25519 detached signature with the configured private key.
  </Step>
  <Step title="Exchange for a session">
    `auth.exchangeSession` returns `abs_...` (15-minute TTL).
  </Step>
  <Step title="Schedule refresh">
    A timer re-runs the exchange at T-2 minutes before expiry. If the refresh budget is exhausted, subsequent tool calls return `SESSION_REFRESH_FAILED`.
  </Step>
</Steps>

## What gets persisted

- The Ed25519 **private key** lives at `ABADGE_PRIVATE_KEY_PATH` (or wherever you stored it) with `0600` permissions. The CLI's `abadge agent add --kind local_mcp` generates one for you.
- The Ed25519 **public key** is stored on the server (`agents.publicKey`).
- Session tokens (`abs_...`) live in MCP server process memory only. Restarting the MCP server forces a new exchange.
- Bootstrap tokens (`abe_...`) are consumed during enrollment and never persisted.

## Audit events

The MCP server emits standard auth audit events:

- `agent.session_issue` (on each successful exchange)
- `agent.session_reject` (on failed signature verification)
- `agent.session_revoke` (on explicit revocation)
- `access.mount_env`, `access.mount_file`, `access.ciphertext`, `access.reveal` — one per tool invocation
